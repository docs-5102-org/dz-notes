## MySQL基础架构

### 整体架构概览

MySQL采用分层架构设计，主要分为两大层次：

#### **Server层**
负责所有跨存储引擎的通用功能，包括：
- 连接器：身份认证与权限管理
- 查询缓存：缓存查询结果（MySQL 8.0已移除）
- 分析器：词法分析与语法分析
- 优化器：生成最优执行计划
- 执行器：调用存储引擎接口执行SQL
- binlog日志模块：归档日志，所有引擎共享

#### **存储引擎层**
采用可插拔式架构，负责数据的实际存储和读取：
- **InnoDB**：默认引擎（MySQL 5.5.5+），支持事务，拥有独立的redo log
- **MyISAM**：早期默认引擎，不支持事务
- **Memory**：内存引擎，数据存储在内存中

## Server层组件详解

### 1. 连接器

**主要职责：**
- 用户身份认证（账户密码校验）
- 权限加载与管理

**工作机制：**
- 用户登录时，连接器验证账户密码
- 验证通过后，从权限表读取该用户的所有权限
- **重要特性**：权限在连接建立时加载，连接期间不受后续权限修改影响

### 2. 查询缓存

**历史功能（MySQL 8.0已移除）：**
- 以`Key-Value`形式缓存SELECT语句及其结果
- Key为SQL语句，Value为结果集
- 命中缓存则直接返回结果

**为何被移除：**
- 缓存失效过于频繁
- 任何表更新都会清空该表的所有查询缓存
- 实际应用场景有限
- 性价比较低

### 3. 分析器

**两阶段分析过程：**

#### 第一步：词法分析
- 识别SQL关键字（如SELECT、FROM、WHERE）
- 提取表名、字段名、查询条件等元素

#### 第二步：语法分析
- 校验SQL语法是否符合MySQL规范
- 检查语句结构是否正确

### 4. 优化器

**核心功能：**
- 在多个执行方案中选择最优方案
- 索引选择策略
- 多表关联顺序优化

**示例：** 对于查询条件 `age=18 AND name='张三'`
- 方案A：先筛选age=18，再筛选name='张三'
- 方案B：先筛选name='张三'，再筛选age=18

优化器会根据统计信息和算法选择执行效率更高的方案。

### 5. 执行器

**执行流程：**
1. 权限校验：验证用户是否有操作权限
2. 调用存储引擎接口
3. 返回执行结果

## SQL语句执行流程

### 查询语句执行流程

以查询语句为例：
```sql
SELECT * FROM tb_student WHERE age='18' AND name='张三';
```

**完整执行步骤：**

```
[连接器] 权限校验
    ↓
[查询缓存] 检查是否有缓存（MySQL 8.0前）
    ↓
[分析器] 词法分析 → 语法分析
    ↓
[优化器] 生成最优执行计划
    ↓
[执行器] 权限二次校验 → 调用存储引擎
    ↓
[存储引擎] 返回查询结果
```

### 更新语句执行流程

以更新语句为例：
```sql
UPDATE tb_student SET age='19' WHERE name='张三';
```

**执行流程（InnoDB引擎）：**

```
[分析器] 解析UPDATE语句
    ↓
[权限校验] 验证更新权限
    ↓
[执行器] 查找目标数据行
    ↓
[InnoDB引擎] 
  1. 将数据更新到内存
  2. 写入redo log（prepare状态）
    ↓
[Server层] 写入binlog
    ↓
[InnoDB引擎] 提交redo log（commit状态）
    ↓
[完成] 事务提交成功
```

## 日志系统与事务一致性

### 双日志机制

#### **redo log（重做日志）**
- **所属层级**：InnoDB引擎独有
- **主要作用**：保证crash-safe能力
- **工作方式**：循环写入，固定大小
- **状态机制**：prepare → commit 两阶段提交

#### **binlog（归档日志）**
- **所属层级**：Server层，所有引擎共享
- **主要作用**：归档备份、主从复制
- **写入方式**：追加写入，不会覆盖
- **记录内容**：完整的逻辑操作日志

### 两阶段提交协议

**为什么需要两阶段提交？**

通过反证法说明：

#### ❌ 场景1：先写redo log，再写binlog
```
1. 写入redo log（commit）
2. 机器崩溃 ← 此时binlog未写入
3. 重启后通过redo log恢复数据
4. 主从同步时，从库因缺少binlog而数据不一致
```

#### ❌ 场景2：先写binlog，再写redo log
```
1. 写入binlog
2. 机器崩溃 ← 此时redo log未写入
3. 重启后无法通过redo log恢复数据
4. 主从同步时，从库通过binlog恢复了该数据
5. 主从数据不一致
```

#### ✅ 两阶段提交流程

```
[步骤1] 写入redo log（prepare状态）
    ↓
[步骤2] 写入binlog
    ↓
[步骤3] 提交redo log（commit状态）
```

**异常恢复机制：**

| 异常时机 | redo log状态 | binlog状态 | MySQL处理 |
|---------|-------------|-----------|----------|
| 步骤1后崩溃 | prepare | 未写入 | 回滚事务 |
| 步骤2后崩溃 | prepare | 已完整 | 提交redo log |
| 步骤3后崩溃 | commit | 已完整 | 事务已完成 |

**关键判断逻辑：**
1. 检查redo log是否完整 → 完整则直接提交
2. redo log为prepare状态 → 检查binlog是否完整
3. binlog完整 → 提交redo log
4. binlog不完整 → 回滚事务

## 总结

### 核心要点

1. **架构分层**
   - Server层：连接器、分析器、优化器、执行器、binlog
   - 引擎层：InnoDB（支持事务+redo log）、MyISAM、Memory

2. **查询语句流程**
   ```
   权限校验 → 查询缓存 → 分析器 → 优化器 → 权限校验 → 执行器 → 引擎
   ```

3. **更新语句流程**
   ```
   分析器 → 权限校验 → 执行器 → 引擎 → redo log(prepare) → binlog → redo log(commit)
   ```

4. **日志机制**
   - **redo log**：保证crash-safe，支持事务
   - **binlog**：归档备份，主从复制
   - **两阶段提交**：确保两个日志的逻辑一致性

### 关键设计思想

- **可插拔存储引擎**：灵活适配不同业务场景
- **查询缓存权衡**：MySQL 8.0移除体现了务实的设计理念
- **两阶段提交**：分布式系统经典的一致性保证方案
- **分层架构**：职责清晰，易于维护和扩展
