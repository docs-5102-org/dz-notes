# Claude Desktop 第三方推理网关（Cowork 3P Gateway）配置指南

> **归档说明（2026-11-06）：** 以下为附件所述客户端与自建网关环境的配置、报错及排查记录，入口和字段规则应以实际版本为准。模型别名不会改变后端模型的真实身份或能力；文中的 Qwen 映射场景不代表官方 Claude 模型支持保证。本次未连接该客户端、网关或推理服务验证。

> 场景：Claude Desktop 通过 Gateway 模式接入本地自建的多渠道聚合代理（one-api / new-api 类），代理背后转发到自托管 vLLM（Qwen3 系列模型）。

---

## 一、入口路径

1. **开启开发者模式**
   - macOS：菜单栏 → Help → Troubleshooting → Enable Developer Mode
   - Windows：登录界面左上角应用菜单 → Help → Troubleshooting → Enable Developer Mode
   - ⚠️ 建议在**未登录 claude.ai 账号**的状态下进行配置（停留在登录页再操作）
2. 顶部菜单 **Developer → Configure third-party inference**，打开配置窗口
3. 左侧导航栏关键分区：
   - **Connection**：选择 Inference Provider（本场景选 `Gateway`），填网关凭证
   - **Workspace restrictions / Connectors & extensions / Telemetry & updates / Usage limits / Appearance / Plugins & skills / Egress Requirements**：其他策略项
   - **Source**：查看/导出底层 JSON 配置
4. 右上角 **Export** 可以把当前配置导出为 `.mobileconfig`（macOS）或 `.reg`（Windows），用于团队批量下发（MDM）

## 二、Gateway 模式的核心概念

```text
Claude Desktop (Cowork 3P · Gateway 模式)
        │  Anthropic Messages API 请求格式 (/v1/messages)
        ▼
本地/远程网关 baseUrl (本例: http://localhost:8317)
        │  多渠道聚合代理（one-api / new-api 等）
        ▼
实际后端模型渠道 (本例: http://172.16.0.235:8001/v1 → vLLM → Qwen3.6-27B)
```

**关键点**：Gateway 模式默认假设后端说的是 **Anthropic Messages API**协议，而不是单纯的 OpenAI 兼容协议。代理层需要做好协议转换/兼容，否则模型发现能过、但实际对话请求可能失败。

## 三、遇到的问题与排查过程

### 问题 1：`Invalid custom3p managed config: baseUrl: must use https (or http on loopback)`

**原因**：`Gateway base URL` 字段的校验规则——
- 允许 `https://` 任意主机
- 允许 `http://`，但主机必须是回环地址（`127.0.0.1` / `localhost`）

**解决**：
- 网关跑在本机 → 直接用 `http://localhost:端口` 或 `http://127.0.0.1:端口`
- 网关在远程主机 → 必须换成 `https://`（可用 Nginx/Caddy 加反向代理和证书解决），或用 SSH 端口转发映射到本地 loopback 做临时调试

---

### 问题 2：`Model discovery — Gateway returned no usable models`

**原因**：Claude Desktop 会调用网关的 `GET /v1/models` 做自动发现，返回的模型即便数量非 0，也会被 Cowork 自己的"可用性过滤器"筛掉（比如缺少期望字段、命名不符合规则等），出现"有数据但 0 个可用"的情况。

**排查方法**：
```bash
# 先确认认证方式，网关通常要求携带 API Key
curl http://localhost:8317/v1/models \
  -H "Authorization: Bearer <Gateway API Key>"

# 如果代理要求 x-api-key 而不是 Bearer，改用：
curl http://localhost:8317/v1/models \
  -H "x-api-key: <Gateway API Key>"
```

**解决**：跳过自动发现，进入 **Models** 区手动添加条目（`+ Add`），界面本身也会提示：
> "Add entries under Models to test inference without discovery."

---

### 问题 3：手动添加模型时报 `Doesn't look like an Anthropic model`

**报错原文**：
> Doesn't look like an Anthropic model: expected a gateway model route referencing an Anthropic model (e.g. claude-sonnet-4-5, anthropic/claude-*). Name routes to match the underlying model.

**原因**：`Model ID` 字段有**双重校验**：
1. 必须和网关 `/v1/models` 实际返回的 `id` **完全一致**（否则请求转发不到正确渠道）
2. 字符串本身必须"看起来像" Anthropic 模型命名，即以 `claude-` 或 `anthropic/claude-` 开头

直接填自建渠道的原始 ID（如 `ntd/Qwen3.6-27B`）必然会被规则 2 拦下，不能直接改名——改了又会跟规则 1（真实 id 匹配）冲突。

**解决方案：在代理层加"别名/模型映射"**

在多渠道代理（one-api / new-api 等）里配置模型别名映射，让代理**对外多暴露一个 Claude 风格的名字**，内部路由到真实模型：

```text
别名（对外暴露给 Claude Desktop）：claude-sonnet-4.6
实际渠道（内部转发）        ：ntd/Qwen3.6-27B（vLLM: Qwen3.6-27B）
```

操作步骤：
1. 代理后台找到"模型重定向 / 模型映射"配置项，新增别名
2. 重新 `curl .../v1/models` 确认新别名已出现在返回列表里
3. 回到 Claude Desktop 的 Model ID 框，填**别名**（不要带任何自定义前缀，如 `ntd/`）

**命名格式建议**：优先用连字符 `claude-sonnet-4-6` 而非点号 `claude-sonnet-4.6`，因为 Cowork 官方示例统一使用连字符（`claude-sonnet-4-5`）。如果点号格式仍被拒绝，改成连字符重新映射一次即可。

## 四、Models 手动条目 —— 各字段说明

| 字段 | 说明 | 建议填法 |
|---|---|---|
| Model ID | 网关 `/v1/models` 返回的准确 id，且需符合 `claude-*` 命名规则 | 例：`claude-sonnet-4-6` |
| Display name | 选择器里显示的名字，留空则自动从 ID 格式化 | 可填便于辨识的名字，如 `Qwen3.6 27B（本地）` |
| Offer 1M-context variant | 声明是否支持 1M 超长上下文，Cowork 不会验证真实性 | 除非确认 vLLM `max_model_len` 支持，否则保持关闭 |
| Tier alias | 该模型在 Cowork 内部对应哪个档位（会影响 Explore / 子任务等内部调用路由） | 主力对话模型选 `sonnet`；轻量/快速子任务可选 `haiku` |

## 五、完整排查 Checklist

- [ ] `Gateway base URL` 是否为 `https://` 或 `http://127.0.0.1(:port)` / `localhost(:port)`
- [ ] `curl <baseUrl>/v1/models` 带上正确认证头（Bearer 或 x-api-key，需和界面里的 `Gateway auth scheme` 一致）能正常返回列表
- [ ] 代理层已配置 Claude 风格别名（`claude-*` 或 `anthropic/claude-*`），并在 `/v1/models` 返回结果中确认存在
- [ ] Models 手动条目里的 `Model ID` 与别名字符串**完全一致**（大小写、符号）
- [ ] 点击 **Test connection**，确认状态点变绿
- [ ] 若 Test connection 通过但实际对话失败，检查代理是否具备 **Anthropic Messages API（`/v1/messages`）兼容层**，而不仅仅是 OpenAI 兼容格式
- [ ] 配置完成后点击右下角 **Apply Changes** 生效

## 六、注意事项汇总

1. **协议层面**：Gateway 模式最终是按 Anthropic Messages API 格式发起推理请求，纯 OpenAI 兼容端点（如原生 vLLM 的 `/v1/chat/completions`）不能直接对接，需要代理层做转换。
2. **命名双重约束**：Model ID 既要和后端真实 id 一致，又要长得像 Claude 模型名——只能通过代理层"起别名"来同时满足，不能直接改 Claude Desktop 里的字段。
3. **1M 上下文开关是声明而非探测**：开错了会在长对话中途报错，不会提前校验。
4. **Tier alias 会影响内部子任务路由**：Cowork 的 Explore 等内置子代理默认走 haiku 档位，如果没有合适的 haiku 级别映射，可能导致部分内部功能异常。
5. **敏感信息**：Gateway API key 等字段建议开启 `Credential kind` 里的 `Static API key`（或按需选其他凭证来源），避免明文长期暴露在配置文件里；导出配置给团队使用时注意脱敏。
