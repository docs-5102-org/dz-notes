## 一、云函数本质是什么？

**一句话：**

> 云函数 = 运行在云端的「无服务器（Serverless）后端方法」

你只负责：

* 写函数代码
* 定义入参、出参

云平台负责：

* 服务器
* 运行环境
* 扩缩容
* 鉴权、日志

---

## 二、uniCloud 云函数调用的核心原理

从技术角度看，**云函数调用本质是一次 HTTPS RPC 请求**，只不过：

* 前端 **不能直接访问服务器**
* uniCloud 在中间做了 **安全代理 + 鉴权 + 路由**

---

## 五、几个关键“幕后细节”（很多人不知道）

### 1️⃣ 为什么前端不用写 URL？

```js
uniCloud.callFunction({ name: 'xxx' })
```

👉 实际上：

* 云平台 **自动映射**
* `name` → 内部云函数路由
* 真实 HTTP 地址对你是隐藏的

---

### 2️⃣ 用户身份是怎么传给云函数的？

```text
前端登录 → uniCloud 保存 token
       ↓
每次 callFunction 自动携带 token
       ↓
云函数 context.auth
```

在云函数中你可以直接用：

```js
exports.main = async (event, context) => {
  const uid = context.auth.uid
}
```

👉 **不用前端传 uid，防止伪造**

---

### 3️⃣ 云函数为什么安全？

| 风险     | 云函数如何避免      |
| ------ | ------------ |
| 伪造请求   | 平台校验 token   |
| 越权     | context.auth |
| 直接连 DB | DB 只对云函数开放   |
| DDoS   | 平台限流         |

| 前端直连         | ❌    | ✅        |

## 七、一个“一句话版流程”

> **uni-app 调用云函数时，前端通过 uniCloud SDK 发起 HTTPS 请求 → 云平台网关校验身份 → 路由到指定云函数实例执行 → 返回结果给前端，全程无需自己维护服务器。**

## 八、什么时候该用云函数？

✅ 适合：

* 小程序 / App
* 中小项目
* 业务 CRUD
* 支付 / 登录 / 订单

❌ 不适合：

* 超长任务（视频转码）
* 强状态连接（WebSocket 高并发）
* 特殊系统级操作

# 一句话先给结论

> **云平台的“自动映射”，本质是：
> 通过「函数注册表 + API 网关 + 路由规则」，
> 把一个 *函数名* 映射到 *真实可访问的执行实例*。**

你看到的“自动”，只是**把复杂度隐藏了**。

---

## 一、先纠正一个误解

❌ **不是**：

> 前端 magically 直接调用某个 JS 文件

✅ **真实情况是**：

> 前端调用的是 **统一入口 API**，
> 平台在后台 **路由到对应云函数实例**

---

## 二、整体架构（高层）

```text
前端
  ↓
云平台 API Gateway（统一入口）
  ↓
函数路由 & 调度系统
  ↓
云函数运行实例（Node.js / Python）
```

---

## 三、自动映射的 4 个关键组件（核心）

### 1️⃣ 函数注册表（Function Registry）

当你部署云函数时，平台会做一件事：

```text
扫描你的云函数目录
  ↓
生成函数元数据
  ↓
写入「函数注册表」
```

### 注册表里一般包含：

| 字段           | 说明            |
| ------------ | ------------- |
| functionName | createOrder   |
| appId        | 小程序 / 应用 ID   |
| runtime      | Node.js 18    |
| entry        | index.main    |
| region       | cn            |
| version      | v12           |
| permission   | auth / public |

📌 **这是“自动映射”的第一步**

---

### 2️⃣ API Gateway（统一请求入口）

前端调用时：

```js
uniCloud.callFunction({
  name: 'createOrder',
  data: {}
})
```

**实际上并不是调用 `createOrder` 的 URL**，而是：

```text
POST https://api.unicloud.xxx.com/call
```

请求体大概是：

```json
{
  "appId": "xxx",
  "functionName": "createOrder",
  "data": {...},
  "token": "user-token"
}
```

👉 **函数名只是一个参数**

---

### 3️⃣ 路由匹配（Mapping 核心）

API Gateway 收到请求后：

```text
解析请求
  ↓
校验 token / appId
  ↓
functionName = createOrder
  ↓
查函数注册表
```

伪代码：

```js
fn = FunctionRegistry.find(appId, functionName)

if (!fn) {
  return 404
}
```

📌 **这一步就是“自动映射”发生的地方**

---

### 4️⃣ 实例调度（真正执行）

如果函数存在：

```text
检查是否有可用实例
   ├─ 有 → 直接调用
   └─ 无 → 冷启动一个新实例
```

```text
把 event / context 注入
  ↓
执行 fn(entry)
  ↓
收集 stdout / log / result
```

## 五、为什么你“看不到 URL”？

因为平台**刻意不暴露**：

| 不暴露的东西 | 原因    |
| ------ | ----- |
| 真实执行地址 | 防攻击   |
| 服务器 IP | 可动态变  |
| 实例数量   | 自动扩缩容 |
| 内部路由   | 安全隔离  |

👉 前端只需要 **函数名 + 数据**

---

## 六、为什么比传统后端更安全？

### 传统后端

```text
前端 → /api/order/create
```

### 云函数

```text
前端 → API Gateway → 内部函数
```

安全优势：

* 无法直接扫接口
* 函数级权限
* 用户身份强绑定
* 内部网络访问 DB

> 📞 **拨分机号（函数名）**
> ☎️ **总机（API Gateway）**
> 📇 **通讯录（注册表）**
> 👨‍💼 **接线员（调度器）**

你只管拨号，不知道人在哪。

## 八、再一句话总结（工程版）

> **云平台通过「函数注册表 + API Gateway + 调度系统」，在部署阶段建立函数名到执行入口的映射，在运行时通过统一入口动态路由到具体云函数实例，这就是所谓的“自动映射”。**
